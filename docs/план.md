# План работ

Как двигаемся от пустого репозитория до работающего сайта. Этапы идут по порядку,
внутри этапа — задачи; этап считается закрытым, когда выполнены его критерии приёмки.

Правило для всех этапов: сначала работает, потом красиво. Вёрстка не блокирует логику.

## Этап 0. Скелет проекта

- [ ] `create-next-app` с TypeScript, Tailwind, App Router
- [ ] Prisma + PostgreSQL в docker compose, первая миграция
- [ ] переменные окружения через `.env.example`
- [ ] линтер и форматтер, `npm run check`
- [ ] CI: сборка и типы на каждый пуш (GitHub Actions, бесплатный план)

**Готово, когда:** `docker compose up` поднимает базу, `npm run dev` открывает
пустую страницу, `npx prisma migrate dev` проходит без ошибок.

## Этап 1. Пользователи и доступ

- [ ] схема `User`, хеширование паролей (argon2)
- [ ] регистрация, вход, выход, подтверждение почты, восстановление пароля
- [ ] роли и проверка прав на сервере (`requireRole`)
- [ ] личный кабинет — заглушка с профилем
- [ ] тесты: чужой черновик недоступен, роль без прав получает 403

**Готово, когда:** можно зарегистрироваться, подтвердить почту, войти и увидеть
свой профиль; попытка открыть чужое возвращает отказ, а не пустую страницу.

Это самый рискованный этап по безопасности — права пишем здесь и больше не трогаем
без тестов.

## Этап 2. Публичная часть

- [ ] схема `Conference`, `Section`, `File`
- [ ] главная: текущая конференция, дедлайны, секции
- [ ] архив и страница конференции
- [ ] страница документов
- [ ] дизайн-токены МГТУ в `globals.css`, шрифт Golos Text
- [ ] админка: создание конференции и секций (минимум, без красоты)

**Готово, когда:** конференция, созданная в админке, видна на главной и в архиве
без ручной правки кода.

## Этап 3. Подача статьи

- [ ] схема `Article`, `Coauthor`, `FileVersion`
- [ ] форма подачи: метаданные, секция, соавторы, файл
- [ ] черновик и отправка, проверка дедлайна
- [ ] загрузка файла: тип по содержимому, лимит размера, UUID-имя
- [ ] защищённая раздача файла через route handler
- [ ] список своих статей и карточка статьи
- [ ] тесты: файл чужой статьи не отдаётся, приём после дедлайна закрыт

**Готово, когда:** автор подаёт статью, видит её в кабинете, скачивает свой файл,
а другой пользователь по прямой ссылке получает отказ.

## Этап 4. Рецензирование

- [ ] схема `ReviewerAssignment`, `Review`, `StatusEvent`
- [ ] назначение рецензента руководителем секции
- [ ] очередь рецензента и карточка проверки
- [ ] форма вердикта с рекомендациями и внутренним комментарием
- [ ] доработка: новая версия файла, история, комментарий «что изменил»
- [ ] статусная модель и её тесты (нельзя перейти из `draft` в `accepted`)
- [ ] сводка по секции в админке

**Готово, когда:** статья проходит полный круг «подана → на проверке → на доработку
→ подана повторно → принята», и в карточке видна вся история с датами и авторами.

Это ядро проекта. Если времени мало — режем всё остальное, но не это.

## Этап 5. Файлы, почта, уведомления

- [ ] письма: подтверждение, назначение, вердикт, финал
- [ ] лента уведомлений на сайте
- [ ] отчёт о проверке оригинальности как вложение к статье
- [ ] поле «пометка о ИИ» для преподавателя
- [ ] экспорт списка статей по секции в CSV (пригодится оргкомитету)
- [ ] резервное копирование базы и загрузок, проверка восстановления

**Готово, когда:** письмо о новом вердикте доходит, бэкап разворачивается на чистой
машине.

## Этап 6. Развёртывание

- [ ] Dockerfile приложения, `docker-compose` с nginx
- [ ] домен и TLS (Let's Encrypt)
- [ ] миграции при деплое, healthcheck
- [ ] логи и простая страница статуса
- [ ] смоук-тест после выката: регистрация, подача, вердикт

**Готово, когда:** сайт открывается по домену, закрыт от прямого доступа к базе,
после перезагрузки сервера поднимается сам.

## Этап 7. Ассистент-рецензент (после запуска)

- [ ] выбор провайдера модели и ключ в переменных окружения
- [ ] извлечение текста из PDF/docx
- [ ] запрос к модели: вердикт + причина + список замечаний
- [ ] хранение ответа как `Review` с `source = ai`, отдельно от человеческих
- [ ] в интерфейсе — блок «мнение ассистента» рядом с формой рецензента
- [ ] учёт цены запросов и лимит на статью
- [ ] запрет: ассистент не меняет статус статьи, только предлагает

**Готово, когда:** рецензент видит предложение ассистента, может его принять,
поправить или проигнорировать, и в истории видно, что это была машина.

## Этап 8. Проверка оригинальности через API

- [ ] договор с сервисом и ключ (задача кафедры, не наша)
- [ ] отправка файла, ожидание результата, сохранение отчёта
- [ ] порог 70% в конфиге, подсветка в карточке
- [ ] поведение при недоступности сервиса — не блокировать подачу

**Готово, когда:** отчёт появляется в карточке статьи автоматически, а при отказе
сервиса подача продолжает работать.

## Состав первой версии к запуску

Минимум, без которого сайт не имеет смысла: этапы 0–4 и 6. Этап 5 можно частично:
письма — да, бэкапы — да, экспорт — по желанию. Этапы 7 и 8 — после запуска.

## Риски

| Риск | Что делаем |
|---|---|
| Права доступа сделаны небрежно — утечка чужих статей | этап 1 отдельно, тесты на каждый обработчик, ревью перед этапом 3 |
| Требования поменяются после разговора с преподавателем | открытые вопросы в ТЗ имеют ответы по умолчанию, меняются без миграций |
| Нет доступа к API антиплагиата | v1 живёт с ручной загрузкой отчёта, автоматика — отдельно |
| Один разработчик и учёба параллельно | этапы идут строго по порядку, после этапа 4 сайт уже можно показать |
| Хостинг на VPS без бэкапов | этап 5 включает проверку восстановления, не только создание дампа |
| Нейросеть в рецензии воспринимается как решение | в интерфейсе ассистент всегда отдельно и подписан, статус меняет только человек |

## Чего сознательно не делаем

- не пишем свой редактор статей и не конвертируем docx в PDF;
- не делаем многоязычность и тёмную тему в v1;
- не делаем мобильное приложение — адаптивная вёрстка закрывает вопрос;
- не строим универсальную CMS: админка знает только конференции, секции, статьи, людей.
