## 1. Что решаем

Сейчас процесс живёт в трёх местах: сайт принимает файл, преподаватель проверяет
его вручную, оргкомитет собирает программы и заключения в Word. Нигде не видно,
на каком шаге статья и кто её держит.

Система должна сделать процесс видимым и не потерять ни один файл:

1. автор подаёт статью в рамках конференции и секции;
2. рецензент получает её, читает и выносит вердикт с рекомендациями;
3. автор видит замечания и подаёт новую версию;
4. оргкомитет видит статусы по всей секции и закрывает приём.

Вторая очередь — ассистент на нейросети, который предлагает рецензенту свою оценку
и причину. Он не заменяет решение человека, а экономит время на первом проходе.

## 2. Границы версии 1

**Входит:**

- публичная часть: главная с текущей конференцией, архив, документы, страница секций;
- регистрация, подтверждение почты, вход, восстановление пароля;
- кабинет автора: черновики, подача статьи, версии файла, история вердиктов;
- кабинет рецензента: очередь назначенных статей, вердикт, рекомендации;
- админка оргкомитета: конференции, секции, пользователи и роли, назначение
  рецензентов, дедлайны, сводка по секции;
- загрузка и безопасная раздача файлов;
- уведомления на сайте, письма по ключевым событиям.

**Не входит в версию 1:**

- ассистент на нейросети (схема данных под него готова, кода нет);
- автоматическая проверка оригинальности через API (в v1 — загрузка отчёта вручную);
- экспорт сборника и программы конференции;
- оплата, DOI, индексирование, интеграция с РИНЦ;
- мобильное приложение, многоязычный интерфейс (только русский).

## 4. Сценарии

### 4.1 Регистрация

Гость указывает логин, почту и пароль (минимальная длина — 8), подтверждает почту
по ссылке из письма, входит. Восстановление пароля — по ссылке на почту.
Роли при регистрации: автор. Рецензент и оргкомитет назначаются вручную.

**[открыто 4.1]** Нужно ли подтверждение почты для всех, или разрешать вход без него
и требовать подтверждение только перед подачей статьи?

### 4.2 Создание конференции

Оргкомитет создаёт конференцию: название, год, даты проведения, место, описание,
обложка, дедлайн подачи, дедлайн доработки, статус приёма. Затем добавляет секции
и назначает руководителей. Опубликованная конференция видна на главной и в архиве.

### 4.3 Подача статьи

Автор выбирает конференцию с открытым приёмом, заполняет:

- заголовок, аннотацию, ключевые слова, язык;
- секцию;
- соавторов (ФИО, организация, почта) и флаг «научный руководитель»;
- файл.

Статья сохраняется как черновик и может правиться, пока не отправлена. После
отправки — статус «подана», файл заморожен, автор получает письмо.
Проверки: секция принадлежит конференции; приём открыт; файл нужного типа и размера;
соавторы заполнены.

### 4.4 Назначение рецензента

Руководитель секции (или оргкомитет) открывает статью и назначает рецензента из
списка преподавателей. Рецензент получает письмо, статья появляется в его очереди.

**[открыто 4.2]** Один рецензент на статью или двое? По умолчанию: один, схема
позволяет добавить второго без миграции.

### 4.5 Проверка

Рецензент скачивает файл, читает, ставит вердикт:

| Вердикт | Что значит |
|---|---|
| Принять | замечаний нет, статья идёт в сборник |
| На доработку | нужны правки, автор подаёт новую версию |
| Отклонить | не подходит по содержанию или оформлению |
| Сомневаюсь | нужен второй взгляд или решение руководителя секции |

К вердикту прикладывается текст рекомендаций (обязателен для «на доработку»
и «отклонить»), внутренний комментарий (виден только преподавателям) и при
необходимости свой файл с пометками.

**[открыто 4.3]** Слепая проверка: видит ли рецензент ФИО и организацию автора?
По умолчанию: видит, как в референсе.

### 4.6 Доработка

Автор видит вердикт и рекомендации, загружает новую версию файла (старая остаётся
в истории), пишет комментарий «что изменил», отправляет повторно. Рецензент видит
обе версии и сравнивает.

**[открыто 4.4]** Нужна ли переписка автор↔рецензент внутри сайта, или достаточно
вердикта с текстом и комментария к новой версии? По умолчанию: достаточно.

### 4.7 Финальное решение

Решение «принята в сборник» ставит оргкомитет (или руководитель секции — по ответу
преподавателя), независимо от вердикта рецензента. Финальный статус виден автору,
статья попадает в список принятых по секции.

**[открыто 4.5]** Кто ставит финальный статус: рецензент, руководитель секции
или оргкомитет?

### 4.8 Закрытие приёма

Приём закрывается автоматически по дате дедлайна; оргкомитет может закрыть раньше
или продлить, изменив дату. После закрытия подача недоступна, существующие статьи
живут своей жизнью.

## 5. Функционал по модулям

### 5.1 Публичная часть

- Главная: текущая конференция — название, дедлайны, даты, место, кнопка подачи,
  список секций с руководителями, блок документов.
- Архив: все прошедшие конференции, каждая со своей страницей.
- Документы: требования, образец оформления, авторская справка.
- Политика обработки персональных данных, контакты.

### 5.2 Кабинет автора

- Список своих статей: конференция, секция, статус, дата последнего изменения.
- Карточка статьи: метаданные, файлы по версиям, вердикты, кнопка «подать новую версию».
- Профиль: ФИО, организация, степень, ORCID (необязательно), смена пароля.

### 5.3 Кабинет рецензента

- Очередь: назначенные статьи со статусом и дедлайном проверки.
- Карточка проверки: файл, метаданные, форма вердикта, прошлые вердикты по этой статье.
- Список уже проверенных.

### 5.4 Админка

- Конференции: создание, публикация, архив, дедлайны.
- Секции: название, руководитель, порядок.
- Пользователи: поиск, смена роли, блокировка.
- Статьи: фильтры по конференции, секции, статусу; назначение рецензента.
- Сводка по секции: сколько подано, на проверке, принято, отклонено.

Связи: конференция → секции → статьи; статья → версии файла → отзывы; отзыв
привязан к конкретной версии, поэтому история не путается после доработки.

**Статусы статьи:**

```
draft ──submit──> submitted ──assign──> under_review
                                          │
                    ┌─────────────────────┼──────────────┐
              revision_required      accepted        rejected
                    │                                   
              resubmitted ──> under_review
```

`accepted` ставит финальное решение; вердикт рецензента «принять» переводит статью
в `under_review` → ожидание финала, чтобы не путать мнение рецензента с решением
оргкомитета. **[открыто 4.5]**

## 7. Файлы

- Форматы: PDF; docx — **[открыто 7.1]**, нужен ли приём .doc/.docx наравне с PDF.
- Проверка типа по содержимому (магические байты), а не по расширению.
- Лимит размера: 20 МБ **[по умолчанию]**, значение в конфиге.
- Хранение: локальный том на сервере, имя файла генерируется (UUID), оригинальное
  имя хранится в базе отдельно.
- Раздача: только через обработчик с проверкой прав, без прямого доступа по пути.
- Удаление: файлы не удаляются физически при замене версии, только помечаются.

## 8. Оригинальность и участие ИИ

Требования конференции: порог оригинальности 70%, участие ИИ не выше 30%.

**Версия 1:** преподаватель загружает отчёт о проверке к статье, сайт хранит его
рядом с вердиктом. Автоматики нет.

**Версия 1.5:** подключение к API сервиса проверки, если кафедра даст доступ.
Антиплагиат.ВУЗ выдаёт API только по договору организации — ключи получает кафедра, не мы.

**Про 30% ИИ — честно:** надёжных детекторов ИИ-текста не существует, все известные
ошибаются в обе стороны. Если у кафедры это экспертная оценка преподавателя, наша
задача — дать поле и напоминание, а не «посчитать процент» и не показывать автору
цифру как приговор.

## 10. Нефункциональные требования

- **Безопасность:** пароли — `scrypt` в прототипе, argon2 в целевой версии; сессии —
  httpOnly-cookie; защита форм
  от CSRF; ограничение частоты попыток входа; проверка прав на сервере в каждом
  обработчике; загруженные файлы отдаются с `Content-Disposition: attachment`.
- **Данные:** персональные данные храним минимально, согласие на обработку при
  регистрации обязательно, ссылка на политику.
- **Доступность:** контраст не ниже AA, навигация с клавиатуры, подписи у полей,
  осмысленные заголовки.
- **Производительность:** публичные страницы — SSR и кэш, карточка статьи за
  < 300 мс при базе до 10 000 статей.
- **SEO:** серверный рендер анонсов и архива, sitemap, мета-теги.
- **Резервные копии:** дамп базы и папка загрузок, ежедневно, хранение 14 дней.
- **Логи:** ошибки приложения и входов, без паролей и содержимого файлов.

Стека два, и это разные ответы на разные вопросы.

Расхождения намеренные, и у каждого названа причина и точка перехода.

### 12.1. Прототип v1.0

| Слой | Выбор |
|---|---|
| Фреймворк | Next.js, App Router, TypeScript |
| ORM и база | Prisma + SQLite (файл `prisma/dev.db`) |
| Авторизация | собственная: `scrypt` из `node:crypto`, сессия в подписанной httpOnly-cookie |
| Валидация | zod |
| Стили | Tailwind CSS + собственные компоненты на токенах МГТУ |
| Формы | серверные actions Next без react-hook-form |
| Файлы | папка `var/uploads`, раздача через `/api/files/[id]` с проверкой прав |
| Тесты | Vitest: права на файл и переходы статусов |
| Запуск | `npm run dev`, без Docker |

### 12.2. Целевая архитектура

| Слой | Выбор | Когда меняем |
|---|---|---|
| База | PostgreSQL 16 | при выкладке на сервер (этап 6 плана) |
| Авторизация | Auth.js (Credentials) + argon2 | когда появятся подтверждение почты и восстановление пароля |
| Стили | shadcn/ui (Radix), lucide-react | когда появятся диалоги и таблицы |
| Формы | react-hook-form + zodResolver | когда форм станет больше двух |
| Развёртывание | Docker Compose: app + postgres + nginx, TLS через Let's Encrypt | этап 6 |

Правило перехода: меняем слой, когда появляется задача, которую текущий выбор
не закрывает, а не заранее «чтобы было как в целевом». Схема данных от SQLite
к PostgreSQL переносится без изменения модели.

## 13. Почему так

- **Next.js, а не Django.** Django отдал бы админку, права и файлы почти бесплатно
  и был бы быстрее в первой версии. Отвергнут по одной причине: проект практический
  и вести его будет Антон, который ориентируется в React и Node и хочет эти навыки
  подтянуть. Код, которого автор не понимает, не развивается.
- **Next, а не Express + React по отдельности.** Server actions и route handlers
  убирают отдельный REST-слой, публичная часть рендерится на сервере — важно для SEO.
  Меньше мест, где что-то рассинхронизируется.
- **SQLite в прототипе, PostgreSQL на деплое.** Docker-демон на машине разработки
  не запущен, и мы не хотим, чтобы каждый запуск начинался с Docker Desktop.
  SQLite даёт ноль настройки и файл вместо сервера; на деплое меняем провайдер
  Prisma и переносим данные, модель остаётся той же.
- **Свои сессии в прототипе, Auth.js в целевой версии.** Подтверждение почты,
  восстановление пароля и несколько провайдеров входа — это работа Auth.js, и
  писать её руками незачем. На прототипе, где есть только вход по паролю, своя
  реализация короче и предсказуемее.
- **shadcn/ui, а не Ant Design.** Компоненты лежат в репозитории как код, доступность
  из коробки, никакого навязанного вида — перекрасим токенами под МГТУ.
- **Файлы на диске, а не в S3.** Объём небольшой, а S3 добавляет зависимость и
  настройку. Переезд — отдельная задача, путь к файлу уже в базе.

## 15. Словарь

- **Конференция** — событие с датами, дедлайнами и набором секций.
- **Секция** — научное направление внутри конференции, у неё руководитель.
- **Статья** — поданный материал: метаданные, файлы, история статусов.
- **Версия** — конкретный загруженный файл статьи.
- **Вердикт** — решение рецензента по версии: принять, на доработку, отклонить, сомневаюсь.
- **Оргкомитет** — администратор системы и владелец конференции.
